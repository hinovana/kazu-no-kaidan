## 1. この文書の役割

本書は、2026-07-21の家庭内印刷レビューで見つかった本文と設問の問題を、再現可能な修正作業へ分解する。

扱うのは、次の品質問題である。

- 本文に現れない内容を補わないと設問へ答えられない。
- 「はじめのよそう」のような表現が、先行する具体的内容を持たない。
- 「みつけたことを話した」と書かれているが、発話内容がない。
- 独立した補助文をランダムに並べることで、発話と情景描写の間に不自然な飛躍が生じる。
- 本文長は条件を満たしていても、意味のある物語部分が短く、設問根拠だけが目立つ。
- 現行の機械検査が、文字列と文役割の一致を確認するだけで、模範解答が本文から意味的に導けるかを保証しない。

本書は、測定能力や設問構成の正本を置き換えない。測定契約は [item-blueprint.md](item-blueprint.md)、生成仕様は [algorithm-draft.md](algorithm-draft.md)、見直しと利用状態は [item-review-and-release.md](item-review-and-release.md) を正本候補とする。本書は、それらへ反映する変更の順序と完了条件を管理する。

## 2. 実地レビューで確認した問題

### 2.1 対象生成物

確認した生成物は、手がかり発見型 `story-clue-discovery.v1` の動物題材である。本文は現行カウント規則で439字、18文であり、「ふつう」の文字数帯370〜570字に入る。

内訳は次のとおりである。

| 区分 | 文数 | 文字数 | 本文全体に占める割合 |
| --- | ---: | ---: | ---: |
| 固定された物語・設問根拠部分 | 10 | 257字 | 59% |
| 本文長に応じて選ばれた補助文 | 8 | 182字 | 41% |
| 合計 | 18 | 439字 | 100% |

文字数そのものは短すぎない。しかし、補助文の多くは人物の知識、予想、判断、行動、結果を変えない。意味のある固定部分では、性格、明示心情、手がかり、確認行動、発見、反応がほぼそのまま設問根拠になる。そのため、読み手には「答えに使う文と、意味の薄い文しかない」文章として見える。

### 2.2 発話内容の欠落

問題のある並び：

> モモは、みつけたことをゆっくり話しました。あたりには、やわらかい光が広がっていました。

「みつけたこと」の内容が本文中に示されず、次の文も発話内容を受けない。情景描写自体が誤りなのではなく、内容を期待させる発話文の直後へ、意味関係を持たない文を置いていることが問題である。

### 2.3 参照先のない表現

問題のある文：

> ふたりは、はじめの予想とくらべました。

これより前に、誰が何を予想したかが書かれていない。「はじめの」は既出内容を指すが、参照先となる命題が存在しない。読み手が「ことりの足あとかもしれない」などを補う必要があり、本文だけで完結しない。

### 2.4 設問④の正答可能性不足

設問④は、主人公が友達へ小さくうなずいたときの気持ちと理由を問う。現行の模範解答は「しるしのひみつがわかって、うれしい気持ち」である。

しかし、動物題材で検査対象にしている根拠断片は、実質的に次の2つだけである。

- 「あしあとのさき」
- 「ちいさくうなずきました」

これだけでは、次を一意に決められない。

- 何が分かったのか。
- 予想が当たったのか。
- 「うれしい」「安心した」「納得した」「わくわくした」のどれに採点上の得点を与えるのか。
- その気持ちの理由として、本文中のどの出来事を書けばよいのか。

したがって、この問題は「模範解答が存在する」だけであり、「本文から採点可能な答えへ到達できる」状態ではない。対象生成物の設問④は採点対象外とするのが妥当である。

### 2.5 機械検査の盲点

現行の `template_answer_evidence_contract` は、主に次を確認する。

- 指定された文役割が存在する。
- 根拠文に指定文字列が含まれる。
- 模範解答に「うれしい」「わくわく」「よろこん」などの許可語が含まれる。

この検査では、「根拠文の内容から模範解答の理由と心情が導けるか」を確認できない。そのため、構造検査が合格しても、正答可能性に問題のある生成物が残る。

## 3. 修正方針

### 3.1 文字数ではなく、物語の意味段階を増やす

本文長を満たすために独立した文を追加する方式から、本文長に応じて意味のある物語段階を追加する方式へ変更する。

```text
現行
固定された答えの根拠
  ＋
独立した補助文をランダム選択

変更後
場面設定
  ↓
観察または発話
  ↓
予想・意図
  ↓
確認行動
  ↓
比較・別の可能性・見直し
  ↓
発見
  ↓
反応・余韻
```

長さを増やす文は、少なくとも次のいずれかの役割を持たなければならない。

- 場面を理解するための情報を与える。
- 人物の知識、予想、意図、評価を更新する。
- 次の行動の理由を作る。
- 複数の観察結果を比較できるようにする。
- 一度考えた可能性を確かめる、修正する、または棄却する。
- 人物間のやり取りを通じて、片方だけでは得られない情報を加える。
- 解決後の人物の反応や関係を示す。

「削除しても物語状態と読み手の理解がどちらも変わらない文」は、文字数調整用の候補へ入れない。

### 3.2 設問に使わない、意味のある余白を持たせる

すべての意味のある文を設問根拠にしない。まず物語として必要な観察、試行、会話、比較、余韻を作り、その一部を設問が参照する。

初期の設計目標は次のとおりとする。

- 「短め」でも、設問の直接根拠ではない意味段階を1つ以上持つ。
- 「ふつう」では、設問の直接根拠ではない観察・やり取り・比較を2つ以上持つ。
- 「長め」では、別の可能性、途中の見直し、人物間の情報差のいずれかを含める。
- 直接根拠文率、物語段階数、設問に未使用の意味段階数をコーパスで記録する。
- 数値の合否閾値は、修正版を人間が解き直してから確定する。文字数だけを品質指標にしない。

「本文を自由に書いた後で設問を付ける」方式へ変更するのではない。測定設計を先に固定する原則は維持しつつ、設問根拠だけでなく、その根拠が自然に成立する物語状態を先に作る。

### 3.3 参照表現をデータ契約にする

次のような表現を、単なる文字列として挿入しない。

- はじめの予想
- みつけたこと
- わかったこと
- そのしるし
- さっきのこと
- 同じもの

テンプレートでこれらを使う場合は、参照先となる命題または文役割を宣言する。参照先が生成されない場合は、その文を使わず、生成または検査を失敗させる。

例：

```ts
interface ReferenceDraft {
  readonly expressionId: string;
  readonly sentenceRole: string;
  readonly refersToRole: string;
  readonly requiredBefore: true;
}
```

型名は実装時に既存の根拠グラフ契約と統合して確定する。目的は、自然言語処理で後から推測することではなく、テンプレートが既知の参照関係を宣言することである。

### 3.4 心情問題を「状況・理解・反応」の連鎖で作る

心情記述問題は、少なくとも次の3要素を持つ。

1. 心情を変える出来事または比較結果。
2. 人物がその意味を理解したことを示す本文上の手掛かり。
3. 問われる人物の発話、表情、動作などの反応。

模範解答の採点要素は、これらのどの要素から導くかを宣言する。

```text
比較結果: 足あととことりの足が同じ形だった
理解: はじめの予想が当たっていたと気づいた
反応: 目を輝かせ、友達に小さくうなずいた
  ↓
許容解: 予想が当たってうれしい／正体が分かって喜んでいる
```

心情語を完全一致させるのではなく、本文と矛盾せず、理由の採点要素を満たす複数の表現を許容する。一方、「理由を書かなくても許可された心情語が含まれれば合格」とする検査は廃止する。

## 4. 本文長の暫定設計

汎用補助文を `extra_count` で追加する方式は廃止し、意味役割付きの展開文数を `expansion_count` で制御する。観察と予想を必須化した手がかり発見型を含めるため、文字数帯は3構造の実測を収める暫定値へ更新した。

| 本文長 | 暫定文字数帯 | 2026-07-25コーパス平均 | 追加する意味段階の例 |
| --- | ---: | ---: | --- |
| 短め | 250〜550字 | 399.9字 | 観察、予想、確認、発見、反応の最短構成 |
| ふつう | 370〜690字 | 554.0字 | 人物ごとの観察、比較、途中の確認、解決後のやり取り |
| 長め | 560〜880字 | 747.4字 | 別の可能性、見直し、離れた根拠、人物間の情報差 |

コーパス平均は3学年 × 5生成プロファイル × 3本文長 × 30seedの1,350件から得た分布値であり、読了負荷の妥当性を示さない。段階Fで意味段階を増やした修正版を印刷し、1年生用紙面の可読性と読了負荷を確認してから、最終の帯を決める。

## 6. 必須テスト

### 6.1 負例

- 「はじめの予想」があるが、予想内容が先に存在しない。
- 「みつけたことを話した」があるが、内容が存在しない。
- 発話直後に、意味関係のない情景文が入る。
- 「小さくうなずいた」だけから「うれしい」を正答にする。
- 比較結果はあるが、主人公が結果を認識した根拠がない。
- 模範解答に許可心情語はあるが、理由の採点要素がない。
- 補助文が正答を別表現で直接教える。
- 長めにしても物語段階が増えず、同じ骨組みへ汎用文だけが増える。

### 6.2 正例

- 具体的な観察から初期予想が生じる。
- 確認行動によって比較可能な結果が得られる。
- 主人公が比較結果の意味を理解する。
- 反応と心情の許容範囲が、出来事と矛盾しない。
- 設問に使われない文も、人物の行動、理解、関係、場面のいずれかへ寄与する。
- 本文長を変えると、文字数だけでなく意味段階が増える。

### 6.3 コーパス指標

合否判定に加え、次を記録する。

- 本文文字数、文数、物語段階数。
- 設問の直接根拠として使われる文数と割合。
- 設問に未使用だが、意味役割を持つ文数。
- 参照表現数、解決数、未解決数。
- 心情問題ごとの出来事、理解、反応の根拠数。
- 同一の汎用補助文がseed群で出現する割合。
- 人間レビューで見つかった別解、読み止まり、意味の飛躍。

## 7. 版と互換性

この修正は児童向け本文、設問、模範解答を変更するため、内部検査だけの互換変更として扱わない。

- 変更した本文構造のtemplate版を上げる。
- 既存itemを同じrevisionのまま書き換えない。
- 本文品質修正はgenerator版 `kokugo-no-tane.prototype.v0.11`、漢字利用契約は `kokugo-no-tane.prototype.v0.12`、根拠グラフの次版は `kokugo-no-tane.prototype.v0.13` とする。
- 旧seedを入力して表面本文が変わる場合は、意図した非互換変更としてfixtureと変更履歴へ残す。
- 旧生成物は、機械検査合格済みでも本文品質修正後の承認済み問題として扱わない。

## 8. 対象外

この修正では、次を同時に実装しない。

- 新しい設問パターンや解答欄。
- 説明文生成。
- 実測難易度ラベル。
- 正式な児童試行や校正。
- AIによる自由本文を自動承認する仕組み。
- 印刷デザインの全面変更。

ただし、本文量が増えた結果として印刷崩れが起きた場合は、修正完了前に必要最小限の印刷調整を行う。

## 9. 完了条件

次をすべて満たしたとき、本計画を完了とする。

- 今回確認した未解決の「はじめの予想」と内容のない発話が生成されない。
- 心情記述問題の理由と心情が、本文上の出来事、理解、反応から採点できる。
- 「ふつう」「長め」が汎用補助文の追加ではなく、意味段階の追加で長くなる。
- 現行3本文構造の負例・正例・コーパステストが合格する。
- 関連する全体テストとTypeScript型検査が合格する。
- 代表fixtureを答えを隠して解き直し、別解と読み止まりを記録している。
- A4横・縦書きの全ページを確認し、欠落、重なり、はみ出し、不自然な改ページがない。
- 修正版を基準に根拠グラフ拡張を開始できるよう、版と互換境界が正本仕様へ同期されている。

## 10. 検証コマンド

実装時は変更範囲に応じた個別テストに加え、少なくとも次を実行する。

```bash
npm run typecheck:kokugo-no-tane
npm test
npm run test:kokugo-no-tane:corpus
npm run build
```

UIまたは印刷へ影響する変更では、次で実ブラウザ表示と印刷プレビューを確認する。

```bash
npm run serve
```
